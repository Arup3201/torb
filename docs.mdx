# Torb Documentation

Torb is the short form for TaskOrbit. It is an application for managing tasks in a project between contributors. The app is built with the intention to encourage contribution to projects.

This documentation explains the backend of the application.

## Folder Structure

The backend follows a very simple idea of folder structure. Any feature that is related to the core idea of the application is written inside the `core` folder. All other features that are simple add-ons to the existing core concept are kept as a seperate folder.

`core` folder has the following modules

- assignees
- comments
- members
- projects
- requests
- tasks
- users

They all are core part of the application. The application has users who create projects. A project has multiple tasks. The project also has members in it. Non-members can request to join the project and the project owner will approve/reject it. A task has assignees who are responsible to work on the task. A task also has comments where users can suggest and talk about solutions.

The `core` folder also implements the `Avatar` type which is used to represent any user data. For example, a project owner is represented as `Avatar`. This folder also defines the constants used inside the core modules. It defines the errors and `txManager`. `txManager` can handle transactions inside services. It also implements some utilities for checking if the user is owner, member or assignee.

Here are the other folders and their role

- `api`: implements the API layer of the services for HTTP request handling.
- `auth`: implement methods manual and openid based authentication.
- `cmd`: contains `main.go` file, the starting point of the application. It also has `app` folder that implements the `App` structure, creates the server and attaches the API endpoints.
- `middlewares`: implements the middlewares for authorization and utilites needed.
- `models`: defines the gorm models of all the core and other persistent objects.
- `notifications`: implements the service for notifying users of the project activies.
- `testdata`: migration for testing.
- `testhelpers`: helper functions to create containers and fixtures for each module testing.

## Authentication & Authorization

The backend supports the manual and openid methods of authentication. In manual method, the backend uses the basic username & password pattern to login. In the OpenID method, the backend supports google based authentication for now.

### Manual authentication

The user can register to the platform with the manual authentication method. User needs to put - username, email, display name and password.

After user registers to the platform, he needs to verify the email address. An email will be sent to the email address with a verification link. User will click on the link and verify the email address.

User will use the email address and password to login to the platform if he has created a manual method based account.

After the login, the user gets access token and refresh token. The access token expires in 15 minutes. The refresh token is valid for 1 week. Refresh token is used to get new access token when the access token expires. When refresh token is used, it rotates the refresh token as well to prevent attacks.

When the login API is called, the refresh token is sent as cookie and the access token is sent in the response body along with the user data.

The cookie has the following properties:

- Name: `TOKEN`
- Path: `/`
- `HttpOnly`, `Secure` and `SameSite=Lax`

The HTTP response contains the following:

```json
{
    "access_token": ...,
    "expires_at": ...,
    "user": {
        "user_id": ...,
        "username": ...,
        "email": ...,
        "display_name": ...,
        "avatar_url": ...,
    },
}
```
